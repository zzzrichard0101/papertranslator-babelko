외부 공식 자료와 현재 병목을 결합한 다음 개선안
조사일: 2026-10-21. 이 문서는 조사·실험 설계이며 아래 후보의 성능이 이 앱에서 입증되었다는 뜻은 아니다.

1. 현재 진단
현재 Qwen 검수 worker를 중단하거나 사용자 번역을 수정하지 않고 최근 응답 로그를 읽었다. 두 개의 최근 600초 표본에서 모델 요청 소요 시간 중 검수 비중은 약 83~87%였다. 한 표본은 검수 368회/490.65초, 교정 54회/73.00초, 재번역 39회/29.37초였다. 다른 표본의 검수 내부 시간은 입력 처리 약 114초, 출력 생성 약 356초였다. 이것은 모델 호출 시간이며 OCR·조판을 포함한 전체 책 시간 비중이 아니다.
현재는 Qwen 한 슬롯/요청당 8192 문맥, f16 KV, 기존 검증 MTP가 사용된다. 실제 응답에 cache_n과 draft_n_accepted가 있으므로 프롬프트 캐시와 MTP는 이미 동작한다. 새로 도입할 기능처럼 속도 이득을 중복 계산하지 않는다.
검수를 가정상 두 배 빠르게 해도 검수 비중 83%인 모델 구간의 전체 가속은 1/(0.17+0.83/2)=약 1.71배다. 전체 문서에는 OCR/출력 시간이 더 있어 이보다 작다. 외부 벤치마크의 토큰/초를 전체 PDF 처리 시간으로 바꾸어 제시하지 않는다.

2. 채택 여부를 먼저 시험할 후보

A. 동일 검수 모델의 두 요청 동시 처리: 속도 우선 실험
근거: llama.cpp는 슬롯과 연속 배치를 제공한다.[1] 현재 한 슬롯을 두 슬롯 후보와 비교한다. 모델 가중치·전체 원문·검수 항목·요청별 문맥·검증 기준을 유지하고 추론을 겹친다. CPU에서 OCR 작업자를 늘리는 실험과 다른 GPU 추론 실험이다.
구현안: 생성 요청과 결과 커밋을 분리한 bounded queue, 최대 두 개의 독립 문서 단위, 결과는 원래 단위 ID에만 연결하고 원래 순서대로 저장한다. 교정은 원래 검수 결과를 받은 뒤 실행한다. 모델 클라이언트 초기화와 체크포인트 커밋은 직렬화하고 통계는 잠금으로 보호한다.
필수 조건: 슬롯 두 개로 늘릴 때 요청별 8192 문맥을 4096으로 줄이지 않는다. 총 문맥/버퍼를 늘려도 24GB 안에 들어가고 CPU 오프로딩이 생기지 않는지 측정한다. OOM·요청 실패·문맥 초과 시 저장된 작업을 보존하고 기존 한 슬롯으로 돌아간다. KV 양자화나 더 작은 본체 모델을 동시에 바꾸지 않는다. 배치 수가 바뀌면 수치 결과도 달라질 수 있으므로 의미 회귀 검사가 필요하다.
판정: 충분한 크기의 동일 입력 집합에서 전체 경과 시간과 p95, 재시도율, VRAM, 검수 오탐/미탐을 함께 비교한다. 여러 번 반복해 실제 이득이 확인될 때만 기본값으로 승격한다. 긴 문단·문장 수가 다른 요청·취소/재개·정적 JSON 스키마도 포함한다.

B. 프롬프트와 검수 스케줄 개선: 같은 검사의 입력/출력 비용 절감
고정 지시와 문서별 불변 문맥을 앞에 두고 매 요청에서 바뀌는 CHECK_IDS를 뒤에 둔다. 현재 형식도 일부 공통 접두사를 재사용하므로 먼저 cache_n/prompt_n을 확인한다.[1] 검수와 교정을 무작위로 오가지 않도록 단계별 큐를 비교하되, 대기 시간이 늘거나 오류 발견이 늦어지는 비용도 기록한다.
현재 faithful 판정에도 ID·판정·근거·빈 설명이 필요하다. 판정과 필요한 반대쪽 근거는 전부 유지하면서 빈 설명의 반복과 중복 필드를 줄이는 응답 형식을 후보로 비교한다. 항목 수가 같아도 누락/순서 착오가 생기면 거부한다. 한글 설명을 강제로 짧게 잘라 오류 근거를 없애지 않는다.
실제 생성된 토큰 수를 줄이는 것과 max_tokens 상한을 줄이는 것은 다르다. EOS로 일찍 끝나는 정상 요청은 상한만 줄여도 빨라지지 않는다. 고정 지시 캐시만 개선해도 출력 생성 비용은 남는다.

C. 문서별 용어와 문맥: 정확도를 높여 재교정을 감소
Hy-MT2는 용어 지정과 서식/구조 보존 지시를 지원한다.[2] 본문에서 반복되는 후보 용어와 약어를 CPU로 먼저 뽑고, 검증된 용어 대응/정의만 작은 문서 사전에 모은다. 매 문단에는 관련 항목만 전달한다. 제목·같은 문장의 앞뒤 절·표 머리글을 구분하고 전체 책을 반복 입력하지 않는다.
다른 문맥의 같은 단어에 사전 번역을 일괄 강제하지 않는다. 예를 들어 일반어와 전문 용어의 뜻을 문서/절 범위에 묶는다. 사전 변경은 번역 캐시의 입력 정체성에 포함하고 해당 용어가 실제로 쓰인 단위만 무효화한다. 기존 번역에 대한 단순 문자열 일괄 치환은 하지 않는다.
측정: 용어 일관성뿐 아니라 초벌에서 발생한 실제 의미 오류, 교정 호출 횟수와 총 시간을 비교한다. 용어 추출에 드는 시간도 포함한다. 사전이 잘못되면 오류가 확산할 수 있으므로 보류된 후보를 사실로 취급하지 않는다.

D. 독립 품질 평가 전용 모델: 먼저 병행 관측
MetricX-24는 정답 번역이 없어도 원문·번역으로 품질을 추정하는 QE 모드를 제공한다. Large는 속도 비교의 후보이며 해당 공개 체크포인트는 Apache-2.0이다.[3] COMET 계열도 평가/후보 선택에 사용할 수 있지만 체크포인트별 언어 범위와 라이선스가 다르다. XCOMET-XL은 연구 후보로 볼 수 있으나 비상업 조건과 접근 동의가 있으므로 공개 앱에 기본 번들하지 않는다.[4]
도입 초기에는 기존 Qwen 검수를 전부 유지한 채 추가 점수와 오류 표식을 저장한다. CPU 실행 또는 별도 단계의 배치 추론을 비교해 GPU 모델 교체 비용을 피한다. 영어→한국어의 부정·조건·수량·주체 바뀜·의도적 누락에 대한 성능을 먼저 확인한다. 단순 유사도는 의미 보존 판정이 아니다.
품질 점수는 검수/교정 순서와 두 번역 후보의 선택을 돕는 데 우선 사용한다. 점수만으로 자동 통과시키는 경로는 따로 검증하기 전까지 만들지 않는다. 두 모델의 동의도 정확도의 증명은 아니다. 현재 모델의 오탐을 독립 평가로 줄일 수 있는지, 반대로 둘 다 놓치는 오류가 무엇인지 분리해서 본다.

E. 번역 모델 후보 비교: 오류 구간에서만 추가 후보 생성
기존 Hy-MT2 30B-A3B/Qwen 조합과 Hy-MT2 7B, TranslateGemma 12B를 영어→한국어로 비교할 가치가 있다.[2][5] 현재 초벌 번역보다 검수가 더 큰 병목이므로 작은 초벌 모델로 바꾸는 것만으로 큰 전체 가속을 주장하지 않는다.
TranslateGemma 공식 입력 문맥은 2K 토큰이고 전용 템플릿을 사용한다.[5] 장문·수식·표·페이지 문맥을 억지로 끼워 넣거나 자르지 않는다. 12B가 다른 27B 모델보다 좋다는 공식 비교는 Gemma 3 기반 비교이며 현재 Qwen 검수 모델보다 좋다는 결과가 아니다.
처음에는 오류가 발견된 문단에만 두 번째 후보를 만들고, 원문 기반 규칙과 독립 평가 및 기존 양방향 검수로 선택한다. 모든 문단을 여러 모델로 중복 번역하는 방식은 기본값으로 두지 않는다. API와 라이선스 비용 외에 VRAM/모델 로딩/평가 시간도 포함한다.

F. OCR과 표의 선택적 업그레이드
현 보완 OCR의 두 CPU 프로세스 실험은 이미 느렸으므로 반복 적용하지 않는다. 다른 접근은 PP-OCRv6의 경량/중간 인식 모델과 PP-StructureV3 표 구조 복구를 어려운 영역에만 쓰는 것이다.[6][7] 공식 성능 수치는 제작사의 데이터/장비 결과이므로 이 PC의 속도로 일반화하지 않는다. 영어 원문을 인식하는 모델 선택과 한국어 출력 처리는 별개의 문제다.
일반 본문은 기존 경로로 처리하고, 기존 OCR과 다른 판독·회전·심한 줄 분할·표 셀 누락이 있는 영역만 더 높은 해상도/새 인식기로 승격한다. 표는 행/열/병합/머리글 ID를 유지하고 문장으로 평탄화하지 않는다. 원문 좌표와 판독 후보를 모두 보존하며 수식/그림을 텍스트로 추측해 덮어쓰지 않는다.
PP-OCRv6의 주 언어 범위에는 영어가 있으나 모든 모델이 한국어를 포함하는 것은 아니다. 한국어 원문 지원을 추가할 경우 별도의 지원 모델을 선택해야 한다. 전체 PDF를 VLM으로 매번 다시 읽는 설계는 비용 비교 후에만 고려한다.

G. 원문부터 출력까지의 영역별 누락 추적: 정확도와 재작업을 동시에 개선
BabelDOC의 IR 기반 구조를 확장한다.[8] 각 원문 영역/문장/표 셀에 불변 발생 ID, 쪽·열·좌표·역할과 출처를 연결한다. 같은 원문을 캐시에서 재사용하더라도 쪽별 발생 위치는 별도로 보존한다.
원문 목록 → 번역 입력 → 검수된 번역 → 최종 PDF 글자/영역의 대응표를 유지한다. 페이지를 넘는 문장은 하나의 의미 그룹으로 번역하되 각 부분의 원래 쪽/영역 대응을 잃지 않는다. 누락이 발견되면 원문 인식, 번역, 조판 중 어느 단계에서 생겼는지 구분해 그 부분만 재처리한다.
현재 본문 생존 검사는 유용하지만 전체 문자열/8-gram 비율만으로 정확한 위치나 모든 절의 보존을 증명할 수 없다. 새 추적은 대상 영역별 글자와 숫자·수식·셀 개수를 확인하고, 충돌이나 잘림이 있는 영역만 다시 조판한다. 검출기 두 개도 모두 놓친 원본 잉크까지 완벽히 안다고 주장하지 않는다.

3. 우선순위가 낮거나 채택하지 않을 방법
- vLLM/WSL: 배치 실험에서 네이티브 llama.cpp가 병목일 때 분리된 추론 백엔드로 비교한다. 공식 vLLM은 Windows 네이티브 지원이 아니어서 WSL 등 실행 환경이 필요하다.[9] 단순 엔진 교체가 현재 GGUF·MTP·VRAM·조판 호환성을 유지한다고 가정하지 않는다.
- 더 강한 양자화, 작아진 문맥, 검수 항목 생략: 품질 유지 조건을 별도로 통과해야 하므로 일괄 적용하지 않는다.
- 무료 클라우드 API를 필수 경로로 삼기: 무료 할당과 모델별 요청/토큰 제한이 있어 긴 책의 안정된 처리 시간을 보장하기 어렵다.[10][11] 키가 없고 현재 앱은 문서 외부 전송을 막고 있으므로 이번 조사에서는 문서를 보내지 않았다. 선택 연결을 만들더라도 기본값은 독립적으로 동작하는 로컬 경로다.
- 전체 문단의 역번역/세 모델 다수결: 매 문단에 추가 생성 비용을 붙인다. 오류가 확인된 일부 후보 비교에 한정해 대조한다.
- 새 모델의 자체 평가 점수만으로 기존 결과보다 좋다고 결론 내리기: 평가 모델 선호와 도메인 편향을 함께 검사한다.

4. 한 번의 검증 작업으로 묶는 방법
고정된 기존 설정을 기준선으로 저장하고, 새 후보는 분리된 실험 설정으로 실행한다. 이 단계에서는 진행 중인 책을 반복 재시작하지 않는다.
검증 문서는 최소 단일/두 칼럼 native, 일반 스캔, 표·병합 표, 수식·코드, 회전·가로 쪽, 긴 책/참고문헌/페이지 이어짐을 포함한다. 공개 영한 참고 자료는 FLORES+/NTREX 등의 사용 조건을 확인해 비교에 사용하되 학술 문서와 독립 평가를 대체하지 않는다.[12][13] 테스트 문서 자체를 개발 예시와 분리한다.
모델 비교는 같은 원문/참고 번역, 오류 탐지 비교는 고정된 정상/오류 대조군으로 진행한다. 부정/only-if/unless/비교 방향/단위/주체 반전과 실제 OCR 오류를 따로 집계한다. 정답 번역의 다른 올바른 표현을 오역으로 처리하지 않는다.
한 변경만 바꾼 A/B로 원인을 확인한 뒤 결합판을 비교한다. 준비부터 최종 PDF까지의 전체 시간, 처리량, p95, 피크 VRAM/RAM, 모델 로딩, 요청/입력/출력 토큰, 재시도, 빠뜨린 오류, 정상문장 오탐, 원문·출력 영역 대응과 쪽별 렌더를 함께 저장한다. 캐시가 빈 새 번역과 캐시 재개를 구분한다.
속도 후보의 승격 목표는 반복 측정에서 전체 중앙 시간이 기준선보다 최소 15% 줄고, 고정 미사용 집합에서 중대한 의미 오류/누락/잘림 미탐이 늘지 않는 것이다. 15%는 채택을 위한 목표이지 현재 달성 수치가 아니다. 오류 개선 후보는 속도 손실을 기록하고 재교정 감소까지 포함해 전체 시간이 유지되는지 확인한다. 점수 평균만 보지 않고 문서 단위 신뢰구간과 실패 사례를 본다. 미탐 0회가 모든 문서의 무오류 보장을 뜻하지는 않는다.

5. 개발 순서
동일 모델 두 슬롯/캐시/응답 비용 실험 + 영역별 출처 추적 + 문서 용어집을 먼저 한 실험판에 넣는다. QE는 처음에는 관측용으로만 붙인다. OCR/다른 번역기는 실패 구간의 비교 후보로 연결한다. 검증이 끝난 후보만 묶어 기본판에 승격하고, 안정판과 체크포인트는 유지한다. 이것은 측정에 따라 속도와 정확도의 균형을 찾는 계획이며, 전 세계 모든 지식을 조사했다거나 최적 성능/무오류에 도달했다는 주장이 아니다.
