# 문서 우주: PDF 구조 지도

왼쪽 **문서 우주**에서 PDF의 한 쪽을 선택하면 원문 페이지와 같은 좌표에 작은 점과 영역이 나타납니다. 문단 후보, 이미지, 표 후보를 클릭해 위치와 처리 상태를 확인할 수 있습니다. 이 화면은 번역 결과를 바꾸지 않는 읽기 전용 진단 도구입니다.

## 화면의 데이터 규칙

| 표현 | 사용한 근거 | 뜻 |
| --- | --- | --- |
| 쪽 | 원문 PDF의 물리적 쪽 순서 | 하단 막대로 이동 |
| 점의 위치 | 원문 PDF 텍스트 블록·이미지·표 후보의 경계 상자 | 원문 배치를 대략적으로 반영 |
| 청록·보라·금색 점 | 각각 텍스트, 이미지, 표 후보 | 요소의 종류 |
| 점의 수 | 텍스트 길이의 제곱근을 바탕으로 한 제한된 밀도 | 영역의 대략적인 분량. 단어 수나 중요도는 아님 |
| 영역 왼쪽 표시선 | 쪽별 처리 증거 | 초록은 한국어 PDF 쪽 생성, 금색은 현재 처리, 주황은 원문 누락 의심 |
| 클릭 | 선택한 원문 영역 | 짧은 원문과 상태 표시. 원문·번역 PDF의 대응 쪽 열기 |

애니메이션은 `QtQuick.Particles`로 그립니다. 마우스를 올리면 점이 밀렸다 돌아오고, 영역을 누르면 짧게 퍼집니다. 한 쪽의 영역은 최대 90개, 활성 입자는 최대 900개로 제한합니다. 화면 설정에서 **부드러운 움직임**을 끄거나 번역 작업이 실행 중이면 입자 애니메이션을 멈춥니다. PDF 분석은 지도를 처음 열거나 새 쪽을 선택할 때 수행하며, 최근 쪽의 추출 결과는 메모리에서 재사용합니다.

## 상태 표시는 어떻게 판단하나요?

한국어 PDF가 존재해도 **그 쪽이 번역 대상으로 선택된 경우에만** 초록 상태가 됩니다. 출력 생성은 의미 정확성의 증명이 아닙니다. 현재 처리 중인 쪽은 작업 상태의 `current_source_pages`를 사용합니다. 주황은 저장된 `source-coverage.json`에 있는 의심 위치와 텍스트 블록이 겹쳤다는 뜻입니다. 이 진단에는 오탐이 있을 수 있습니다. 번역하지 않기로 선택한 쪽은 별도로 표시합니다.

그림 안의 글자, 스캔 이미지에만 들어 있는 글자, OCR이 놓친 글자는 점으로 따로 나타나지 않을 수 있습니다. 페이지 전체가 하나의 스캔 이미지이면 이미지 한 영역으로 보이는 것이 정상입니다. 표는 PDF 선과 글자 배치에서 찾은 **후보**이며 복잡한 표를 놓치거나 잘못 찾을 수 있습니다. 점 하나가 문장 하나를 뜻하지 않습니다. 대체로 PDF의 텍스트 블록 하나에 여러 점을 놓습니다.

## 시각화 참고 자료와 선택 이유

- [Gather Lite](https://gather.be-of-dao.com/): 마우스에 반응하는 이미지 파티클의 움직임을 미적 참고로 삼았습니다. PDF 데이터 구조와 코드를 가져오지 않았습니다.
- [Docora](https://ojs.aaai.org/index.php/AAAI/article/view/42342): PDF 캔버스, 텍스트, 그래프의 연결이 유용하다는 사례입니다. 여기서는 그래프보다 **원문 좌표와 번역 상태의 연결**을 먼저 구현했습니다.
- [TextArc](https://www.futureofthebook.org/mckenziewark/gamertheory30/textarc/index.html): 텍스트의 분포를 한눈에 보여주고 클릭해서 위치를 찾는 방식이 탐색에 유효하다는 사례입니다.
- [Paperscape](https://paperscape.org/): 과학 논문의 관계를 입자 지도처럼 다루는 참고 사례입니다. BabelKO의 점은 논문 간 인용 관계가 아니라 **한 PDF 내부의 실제 배치**를 따릅니다.
- [Qt Quick Particle System Performance Guide](https://doc.qt.io/qt-6/qtquick-particles-performance.html): 입자 수와 마우스 상호작용 비용을 관리하는 기준입니다.

다음 개선 후보는 쪽 전체를 보는 축소 지도, 영역과 번역문을 함께 강조하는 연결선, 큰 문서에서 쪽 이동 시 PDF 분석을 별도 프로세스로 보내는 방식입니다. PyMuPDF는 여러 스레드에서 동시에 사용하는 것을 지원하지 않으므로 추출을 비동기화한다면 [프로세스 방식](https://pymupdf.readthedocs.io/en/latest/recipes-multiprocessing.html)을 사용해야 합니다.
